## 6. Deletion and residue

**Deletion** is part of the run: D14 on `B` (S2.13) and on `A` (S3.14). `productDelete` "Permanently deletes a product
and all its associated data, including variants, media, publications, and inventory items", removes it "from all
associated collections" (`productDelete.md:122-133`). Units are zeroed before (S3.7, S3.12) so the deleted items'
history nets to 0; idempotency keys expire by themselves after 24 h (`implementing-idempotency.md:56`).

**Clean-up from any state** (a run that dies anywhere, or the guard's abort) — `cleanup(RUN_ID)`:
1. Candidates = the product ids in the run log ∪ the products of test-only `productVariants(first: 10, query:
   "sku:ZZF73LT<RUN_ID>") { nodes { product { id } } }` ∪ test-only `products(first: 10, query: "title:ZZ-F73-LIVETEST*")`.
   When the log shows a create / duplicate sent without its answer, poll both searches every 10 s for 60 s.
2. Each candidate is read with test-only `product(id:) { title vendor variants(first: 5) { nodes { sku } } }` and deleted
   by D14 **only if** its title starts with `ZZ-F73-LIVETEST <RUN_ID>`, its vendor is `ZZ-F73-TEST` and every variant's
   SKU is `ZZF73LT<RUN_ID>`. A product failing the check is never touched: it is reported.
3. Then S4. The clean-up needs no state but `RUN_ID`: re-runnable, idempotent by state.

**Residue proof (S4)** — all must come back empty:
